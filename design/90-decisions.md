### 2026-09-05 — Site search via `@easyops-cn/docusaurus-search-local`, a new dependency on the base image, not this repository
Context: The blog had no search. This repository does not own the shared Docusaurus runtime (`AGENTS.md`, *Project identity and boundary*) — there is no `package.json` under `docs/`, and every npm dependency the site can use comes baked into the immutable `ghcr.io/the-running-dev/docs-template` image built from the sibling `Docs-Template` repository. Adding a search theme therefore means adding a dependency there, not here, plus a decision entry here since it is this repository's `docusaurus.config.ts` that will register and configure it.
Chosen: `@easyops-cn/docusaurus-search-local` (resolved `0.55.3`), added to `Docs-Template`'s `package.json`/`pnpm-lock.yaml` on branch `feature/search-local-theme` (pushed; PR not yet opened/merged). Verified locally in that repo by temporarily enabling it in its own `docusaurus.config.ts` and running `pnpm run build:prod` against Docusaurus 3.10.1 — it built cleanly and produced `search-index.json` and a `/search` route; the temporary config enable was then reverted there since consumer sites (this one) own their own `docusaurus.config.ts` and the template's `COPY . .` overlay (`docs/Dockerfile`) replaces it entirely. This repository's `docusaurus.config.ts` gains the `themes` entry once the new image is published and `docs/Dockerfile`'s `BASE_IMAGE` digest is bumped to it — that step is sequenced after the `Docs-Template` PR merges and its release workflow publishes the new image (`Docs-Template/.github/workflows/release.yml`).
Rejected: **Algolia DocSearch** — no new npm dependency if bundled, but requires either applying to Algolia's free program and waiting on approval, or running a paid account with a crawler, plus storing `appId`/`apiKey`/`indexName`; a local, build-time index has no external account or secret and matches this repository's self-contained publishing pipeline (`agent.md`). **Vendor/fork a local search implementation into this repository instead of depending on the base image** — would avoid the two-repository dependency entirely, but this repository has no runtime of its own to attach it to (no `package.json`, no bundler); the search UI has to live in whatever Docusaurus instance renders the site, which is the base image.
Reversibility: cheap on this side (a `themes` array entry and a `BASE_IMAGE` digest, both revertible without touching content or routes); the `Docs-Template` dependency addition is also cheap to revert there, but removing it after other consumers of that image start relying on it would not be.

### 2026-08-24 — S37's console workspace depends on `@subzerodev-git/console` via an unversioned `file:` path, plus its React/Vite toolchain
Context: S37 ports the blog's post-list and compose screens (previously `tools/blog-mcp/ui/`) into a second, separate console app under `tools/git-service-consumer/console/`, registered against the base `SubZeroDev.GitService` package's view-registration surface (`createConsole`, `ConsoleViewRegistration`). That package is not published to a registry; something has to name how this new workspace resolves it, and building it at all first requires a React/Vite/TypeScript toolchain this repository had not previously carried.
Chosen: `tools/git-service-consumer/console/package.json` depends on `"@subzerodev-git/console": "file:../../../../SubZeroDev.GitService/console"`, a sibling-checkout relative path -- both repositories already sit side by side under `Dropbox/Projects/` in every environment this runs in, the same physical layout the 2026-08-21 `SubZeroDev.GitService` decision ("S20's derived-image build reaches the base's source via a sibling checkout and Docker's `--build-context`") relies on, though that entry covers a different mechanism (BuildKit `--build-context` source copying, not an npm package dependency) and is not itself authority for this one. Alongside it: `react`, `react-dom` (the base package's own peer expectation, since its exported components are React components), and `vite`/`@vitejs/plugin-react`/`typescript` as the build toolchain, matching the versions and shape `tools/blog-mcp/ui/` (and the base's own `console/`) already use, so nothing here introduces a second convention for how a console app in this repository is built.
Rejected: **Publish `@subzerodev-git/console` to an npm registry and depend on a real semver range** — the strongest fix for the unpinned-path risk (no lockfile integrity hash, unusable without the exact sibling checkout present), but publishing the base package outward is a `SubZeroDev.GitService`-side decision this slice has no standing to make, and was already explicitly declined once for a related question (`SubZeroDev.GitService`'s own 2026-08-21 entry: "explicitly out of scope for S35"). **Git submodule the base's `console/` directory into this repository** — would give a pinned, lockfile-visible reference without needing a registry, but this repository's conventions name no submodule usage anywhere and a submodule adds update/pin ceremony a sibling-checkout `file:` dependency avoids; also does not remove the "another repository must be checked out alongside this one" precondition the `file:` path already has. **Fork/vendor the base's console view-registration code directly into this workspace instead of depending on it** — removes the cross-repo coupling entirely, but duplicates the base's `createConsole`/`ConsoleViewRegistration`/`eligibleViews` machinery, which is exactly the kind of drift-prone copy `AGENTS.md`'s *Single ownership* section exists to prevent; rejected in favor of a real (if unpinned) dependency on the one canonical implementation.
Reversibility: cheap for the toolchain (devDependencies, revert by deleting the workspace); more expensive for the `file:` dependency choice specifically, since replacing it with a published package later means updating this entry and re-resolving anyone's local checkout layout.

### 2026-08-13 — Footer activated as a config-only outbound bar, no `@theme/Footer` swizzle
Context: `docusaurus.config.ts` carried `footer: { style: 'dark', links: [] }` since install, which the stock `@theme/Footer` renders as `null` — confirmed by building the site and finding zero `footer` occurrences in the served HTML. The apex/blog reconciliation that produced this entry asked for a four-link outbound row mirroring the masthead's ecosystem group (`SubZeroDev.com`, `Blog` marked current, `Projects`, `Portfolio`), and left open whether that needs a swizzled `@theme/Footer` or can ship through config alone.
Chosen: Config alone. Reading the shipped `@docusaurus/theme-classic` source showed `Footer/LinkItem` forwards a per-item `className`, so `footer.links` as a flat (non-multi-column) array renders through `Footer/Links/Simple` with the same `footer__link-item` elements the masthead's `.navbar__link` styling already has a pattern for. The `Blog` entry reuses the masthead's own `site-masthead__ecosystem-active` class name rather than inventing a second one, and `docs/src/css/custom.css` gains a footer-scoped block that mirrors the masthead's link treatment (mono uppercase, underline, `--fg` on hover/current, external-link glyph hidden) plus a rule hiding the Simple layout's `·` separators in favour of gap-based spacing, matching the masthead's bar. `.footer`'s border/background rule already existed in `custom.css` from install and had never rendered anything — this activates it rather than adding new dead CSS.
Rejected: **Swizzle `@theme/Footer`** — would allow arbitrary markup (e.g. an exact copy of the masthead's DOM structure), but the stock Simple-links layout already produces the same shape once styled, and a swizzled component is a second place the ecosystem group's four links can drift from the masthead's; rejected because config-only keeps one link list in source (still two, `docusaurus.config.ts`'s navbar items and footer.links, but no new React component to maintain). **Carry `apexFooterQuote` in the footer** — the reconciliation's own framing flagged this as recreating the un-derived-literal problem the `sinceYear` pin was written to fix; not done.
Reversibility: cheap

### 2026-08-11 — The masthead uses the apex box model and names SubZeroDev.com in the shared links
Context: visual comparison after the first masthead release showed that the blog used the apex tokens but not its geometry. Docusaurus' global `border-box` rule made the 1,120 px masthead include its horizontal padding, while the apex's `page` primitive adds that padding outside a 1,120 px content column. The owner also wants both sites to carry an explicit `SubZeroDev.com` destination before the existing ecosystem links.
Chosen: Reproduce the apex `page > stack > header, nav, rule` structure locally: a content-box frame, the same responsive external padding, the same nested stack gaps, the same 880 px identity measure, and a separate rule after the navigation gap. Keep the linked `SubZeroDev` wordmark, suppress Docusaurus' external-link glyphs in this header, and make the shared right-hand group `SubZeroDev.com`, `Blog`, `Projects`, `Portfolio`, in that order. On narrow screens the local Explore control remains separate and the four shared links wrap beneath it without horizontal overflow.
Rejected: **Adjust the existing padding and margins in place** — fewer lines changed, but leaves two unrelated boxes approximating one apex stack and makes the next spacing change drift again. **Remove the linked wordmark because the apex heading is plain text** — visually exact, but explicitly declined; the link is useful and has no effect on the resting appearance. **Put SubZeroDev.com only on the wordmark** — already true, but does not create the shared explicit link row the owner intends to mirror on the apex site.
Reversibility: cheap — the routes are unchanged and the wrapper, one navigation item and scoped CSS can be reverted independently of site content.
