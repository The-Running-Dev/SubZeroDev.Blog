### 2026-08-11 — The masthead uses the apex box model and names SubZeroDev.com in the shared links
Context: visual comparison after the first masthead release showed that the blog used the apex tokens but not its geometry. Docusaurus' global `border-box` rule made the 1,120 px masthead include its horizontal padding, while the apex's `page` primitive adds that padding outside a 1,120 px content column. The blog wordmark and navigation therefore sat 64 px farther inward at a 2,048 px viewport, and the rule immediately followed the navigation instead of participating in the apex stack rhythm. The owner also wants both sites to carry an explicit `SubZeroDev.com` destination before the existing ecosystem links.
Chosen: Reproduce the apex `page > stack > header, nav, rule` structure locally: a content-box frame, the same responsive external padding, the same nested stack gaps, the same 880 px identity measure, and a separate rule after the navigation gap. Keep the linked `SubZeroDev` wordmark, suppress Docusaurus' external-link glyphs in this header, and make the shared right-hand group `SubZeroDev.com`, `Blog`, `Projects`, `Portfolio`, in that order. On narrow screens the local Explore control remains separate and the four shared links wrap beneath it without horizontal overflow.
Rejected: **Adjust the existing padding and margins in place** — fewer lines changed, but leaves two unrelated boxes approximating one apex stack and makes the next spacing change drift again. **Remove the linked wordmark because the apex heading is plain text** — visually exact, but explicitly declined; the link is useful and has no effect on the resting appearance. **Put SubZeroDev.com only on the wordmark** — already true, but does not create the shared explicit link row the owner intends to mirror on the apex site.
Reversibility: cheap — the routes are unchanged and the wrapper, one navigation item and scoped CSS can be reverted independently of site content.

### 2026-08-11 — The blog carries the SubZeroDev.com masthead and a distinct publication rail
Context: the blog already used the apex site's palette and typography, but its conventional Docusaurus navbar made a move between `subzerodev.com` and `blog.subzerodev.com` read as a change of product. The requested outcome is one global identity without coupling the Docusaurus consumer to the apex site's landing-page runtime.
Chosen: Render the complete static apex masthead on every blog, post, hub and docs route: the `SubZeroDev` brand, `Professional uncertainty since 2026.`, and `Well… Why not?`. Keep the apex ecosystem group on the right as `Blog`, `Projects`, and `Portfolio`; make `Blog` the visible active destination here. The left group remains blog-local but becomes `Latest`, `Archive`, `Topics`, `Series`, `Builds`, `About`, and `Docs`, retaining every prior destination while avoiding duplicate `Blog` and `Projects` labels. On narrow screens the masthead and ecosystem group remain visible; an `Explore` drawer carries only the local group and preserves the existing Series and Builds submenus. The apex source is canonical and the blog owns only its Docusaurus translation, with no new shared package or runtime dependency.
Rejected: **Keep the current labels** — least disruptive wording, but it repeats `Blog` and `Projects` beside the preserved ecosystem links and obscures which destinations are local. **Reduce the rail by removing Series and Builds** — shorter navigation, but hides still-supported hubs from their current discovery point. **Put every link inline on mobile** — visually closest to the apex mobile page, but ten local and global destinations make the header substantially taller and nested menus harder to operate. **Create a shared runtime component** — strongest drift prevention, but a cross-repository package change is disproportionate to a consumer-specific Docusaurus translation and would bind two different renderers unnecessarily.
Reversibility: cheap — the blog-local theme override, navigation configuration and artifact assertions can be changed without altering routes or the apex site.

### 2026-08-03 — Auto-merge stays; the kit's external-writes rule is scoped around it
Context: Installing the agent kit. The kit requires explicit authorization before merging or deploying. This repository instructs the opposite in eight places — open a ready pull request and enable automatic squash merge, with a draft only on explicit request — so an agent ships to GitHub Pages without a human gate by standing policy. Both rules cannot sit in one file.
Chosen: This repository's practice wins, as the installer requires. The kit's external-writes rule installs with merge and deploy carved out, and the carve-out says *why*: the gate here is the two required checks plus conversation resolution, enforced by branch protection, not a human reading the diff. Stated explicitly so a future reader does not "correct" it back.
Rejected: **Adopt the kit's rule and drop auto-merge** — puts a human between an agent and a live site, and matches the sibling engine repository; rejected because 100+ merged pull requests and the whole `tools/blog-mcp` publishing pipeline are built around auto-merge, and the required checks are the real gate. **Split by change type** — auto-merge for posts, authorization for code; already half-present in the existing wording, but a conditional rule is the one an agent misapplies under pressure.
Reversibility: cheap
